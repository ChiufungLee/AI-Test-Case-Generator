## D-001 · 2026-10-01 · 流程：新功能分支独立开发 + 计划模式前置

**决策**：所有新功能在独立分支上开发（分支名沿用现有 `type/scope` 惯例，如 `feat/test-assets`）；写代码之前必须先走计划模式产出实施计划并获得确认。

**原因**：（1）功能开发与 main 隔离，main 始终可用；（2）计划先行把方案分歧暴露在写代码之前，避免返工；（3）仓库历史本就按功能分支合并（如 `docs/update-readme-screenshots`、`refactor/func-to-knowledge-pages`），此条将其固化为硬性流程。

**状态**：生效中

## D-002 · 2026-10-01 · 路线：按五阶段推进测试资产闭环

**决策**：产品演进顺序：① 测试资产化（发布/查看/人工编辑/版本）→ ② API 测试工作台（OpenAPI 导入 + Schema 规则引擎 + 测试设计生成 + 进程内执行）→ ③ Runner 抽象与 UI 自动化（Playwright 等）→ ④ AI 失败分析深化 → ⑤ CI Webhook 接入。执行能力并入第②阶段而非单列；"增加更多质量分析 Agent"暂缓。

**原因**：当前平台链路终止于 CSV 导出（`api/endpoints/workflow_api.py` 的 export 端点），"生成 → 导出 → 人工处理"没有闭环，断点在"用例无法沉淀为资产、资产无法执行"。API 执行本质是 HTTP 调用，成本远低于单列一个"执行阶段"，并入②使平台在第二阶段末即第一次具备真实执行能力。否决的备选：先做更多 AI 分析类功能——分析质量的边际收益低于闭环完整性。

**状态**：生效中

## D-003 · 2026-10-01 · 架构：LLM 一律走结构化输出链，不做 function-calling 工具层

**决策**：所有 LLM 调用（含未来"AI 修改用例"）通过 `_invoke_structured` 的解析链（纯文本 JSON 优先 → 截断抢救 `_salvage_truncated_json` → `with_structured_output` 兜底，失败重试 1 次）；不采用"给 AI 提供 search_test_cases()/update_test_case() 等工具"的 agent 工具调用路线。工具层语义由代码直接调用的确定性服务函数承担，LLM 只负责产出结构化数据。

**原因**：实测（记录于 AGENTS.md）DeepSeek 思考模式下复杂 prompt 自动触发思考，此时强制 `tool_choice` 一律 400；agent 工具路线在本项目的 LLM 栈上不可依赖。

**状态**：生效中

## D-004 · 2026-10-01 · 范围：用例的 AI 修改延后至 1.5 期

**决策**：资产化第一期只交付发布 / 查看 / 人工编辑 / 版本管理 / 版本对比 / 回滚 / 导出；"AI 修改用例"作为 1.5 紧随其后。数据模型预留 `TestCaseSetVersion.source_type = 'ai_edit'` 枚举值。

**原因**：第一期先保证资产化独立可上线、价值自足；AI 修改的确认流程依赖版本 diff 展示，复用第一期建好的 diff 服务函数与前端组件成本显著更低。模型预留避免 1.5 期再做迁移。

**状态**：生效中

## D-005 · 2026-10-01 · 架构：测试资产独立建表，Artifact 保持"运行产物溯源"定位

**决策**：新增 `test_case_sets` / `test_case_set_versions` 表承载资产，Artifact 表结构不动。资产对工作流的溯源用可空弱关联（`source_workflow_id`、`source_artifact_id`，ondelete=SET NULL）。

**原因**：Artifact 被 workflow 作用域锁死——唯一约束含 workflow_id、随 Workflow 级联删除——而资产需要独立生命周期（owner、可见性、被执行/Bug 引用）。工作流删除后资产必须存活，故溯源只能弱关联（删除后溯源字段置空，内容不受影响）。否决的备选：把 Artifact"升级为资产基础数据层"——会破坏其运行溯源语义，且级联删除行为对长期资产是危险的。

**状态**：生效中

## D-006 · 2026-10-01 · 架构：用例集版本以整集 JSON 存版本行，不做用例级拆表

**决策**：`test_case_set_versions.content` 存与 Artifact 同构的 `{"test_cases": [...]}` JSON；不把用例拆成行级表。未来执行结果以 `(set_id, version, case_id 字符串)` 引用用例。

**原因**：单集规模上限 40 条（`_dynamic_case_limit` = clamp(需求点数×3, 10, 40)）；本期及可预见的操作全部是全集操作（发布、AI 全量修改、CSV 导出、diff、执行输入），Python 内按 case_id 计算 diff 足够；整集 JSON 与 Artifact 语义对齐，AI 修改天然全量进出。**重新评估的触发条件**：出现按用例维度的数据库查询/索引需求（如跨资产检索用例、执行结果需要外键完整性）——届时从 JSON 解析派生行级表即可，迁移成本不高。

**状态**：生效中

## D-007 · 2026-10-01 · 设计：一个工作流至多发布一个资产，重复发布追加版本

**决策**：`publish_from_workflow` 首次执行创建资产 + v1；同一工作流重新生成用例后再次发布，在已关联资产上追加新版本（`source_type=publish`，记录新的 `source_artifact_id`）。

**原因**：让"发布"语义稳定为"把工作流最新用例同步进资产"，用户无需理解资产与工作流的版本对应关系；版本链自动保留每次同步的溯源。否决的备选：每次发布新建资产——会产生指向同一工作流的多个平行资产，列表噪音大且资产身份不连续。

**状态**：生效中

## D-008 · 2026-10-01 · 设计：用例编辑采用全量替换 + base_version 乐观锁

**决策**：编辑端点接收完整用例集内容 + `base_version`；服务端先 `TestCaseSet.model_validate` 校验，再以条件更新 `UPDATE ... SET current_version = current_version + 1 WHERE id = ? AND current_version = :base_version` 原子推进版本号，rowcount 为 0 即返回 409。不提供用例级 PATCH；并发冲突不做三方合并，前端引导"加载最新版本"。

**原因**：与现有产物编辑校验模式一致（`/approve` 端点对 analysis 的 model_validate + 422 处理）；全量替换原子性好、实现简单，40 条规模下局部更新无收益。条件更新的并发控制思路对齐 `try_claim_workflow` 的状态机乐观锁。

**状态**：生效中

## D-009 · 2026-10-01 · 设计：资产 owner 外键用 CASCADE 非空，而非 KnowledgeBase 的 SET NULL

**决策**：`test_case_sets.owner_user_id` 为非空、`ondelete=CASCADE`（对齐 `workflows.user_id`），而非 `knowledge_bases.owner_user_id` 的可空 SET NULL。

**原因**：资产是纯 DB 数据，删除用户级联删除资产无副作用；知识库用 SET NULL 大概率与其删除牵涉 ChromaDB 集合清理的后台任务有关，资产没有这类外部资源。**已知不一致点**：同为用户资产，知识库与用例集在用户删除时行为不同；若未来产品要求"注销后资产可交接/保留"，需改为 SET NULL 并补管理员交接逻辑。

**状态**：生效中

## D-010 · 2026-10-01 · 设计：重复 case_id 在发布与编辑入口校验拒绝（422）

**决策**：`TestCaseSet` 在 Pydantic 字段校验之外，额外要求集合内 case_id 唯一；发布与内容编辑两个入口都执行该校验，违反返回 422 并明确提示重复的编号。

**原因**：版本 diff 按 case_id 键控、未来执行结果按 case_id 引用，唯一性是这两个机制的前提。生成端不保证唯一（截断抢救场景可能产生重复编号），必须在资产入口把关；拒绝并提示比静默去重更安全——用户应当知道生成了重复用例。

**状态**：生效中

## D-011 · 2026-10-01 · 命名：导航「测试工作台」，术语「测试用例集」，代码 test_asset、路径 /api/test-sets

**决策**：用户可见文案：导航项「测试工作台」、资产称「测试用例集」、溯源称「来自测试任务」；代码与 API：服务模块 `test_asset_service`、路径 `/api/test-sets/...`、页面路由 `/testbench`。

**原因**：延续既定文案约定（用户可见一律「测试任务」、不用「工作流」）；"工作台"为后续执行功能预留同一模块空间，第一期只增加一个导航项，避免导航膨胀。否决的备选：「测试资产中心」（偏内部视角，用户感知弱）、「用例库」（后续还要容纳执行入口，语义偏窄）。

**状态**：已推翻（导航项「测试工作台」由 D-026 取代、用户可见术语「测试任务」由 D-039 取代；「资产称测试用例集」与代码/路径命名 `test_asset`、`/api/test-sets` 仍沿用本决策）

## D-012 · 2026-10-01 · 架构（方向性）：测试执行第一版用进程内 httpx，Runner 抽象推迟

**决策**：第二阶段的执行能力用进程内异步 httpx 执行 API 用例，复用工作流已验证的基建模式（后台 asyncio 任务 + 事件重放 SSE + 状态机乐观锁）；第一版不引入 subprocess / pytest / Docker 等 Runner 抽象。

**原因**：API 测试的执行本质是 HTTP 调用，无需进程隔离；建议方案中的 `subprocess.run(pytest)` 对 API 用例反而引入进程管理与输出解析负担。**重新评估的触发条件**：引入 UI 自动化（Playwright 需要浏览器进程与隔离）或负载测试时，再抽象 Runner 层。

**状态**：生效中（方向性，未实施）

## D-013 · 2026-10-01 · 设计：source_workflow_id 加数据库唯一约束（细化 D-007）

**决策**：`test_case_sets.source_workflow_id` 增加 `UniqueConstraint("source_workflow_id", name="uq_test_case_set_source_workflow")`。"一个 workflow 至多对应一个资产"由数据库强制，而非仅靠应用层先查后插。发布创建资产路径捕获 IntegrityError → 回滚 → 返回 409 并发冲突。

**原因**：应用层"先查后插"存在并发窗口——两个并发发布都可能查不到关联资产而各自插入，产生指向同一工作流的两个平行资产，直接违反 D-007。SQLite 与 MySQL 的唯一约束均允许多个 NULL，工作流删除（SET NULL）后不受影响，也不妨碍未来独立创建的资产。

**状态**：生效中

## D-014 · 2026-10-01 · 设计：版本语义分离，parent 恒为当前版本且不对外开放（细化/修正 D-008）

**决策**：`parent_version_id` 语义固化为"这个版本在谁的基础上产生"——恒等于乐观锁校验通过的 base_version 对应版本行，由服务层内部推导，`save_new_version` 不对外暴露 parent 参数；`rollback` 的内容来源用独立字段 `source_version_id`（自引用 FK，仅 rollback 使用）记录。版本链严格线性：回滚 v5→v2 产生 v6 时，v6.parent=v5、v6.source_version_id=v2，而非 v6.parent=v2。

**原因**：原设计让 rollback 的 parent 指向历史版本，版本关系会分叉成树，"版本演进"语义被破坏；对外开放 parent 参数则可能在并发下制造不受控的链。两个概念分开后，publish / manual_edit / ai_edit / rollback 遵循同一条简单规则：**任何新版本都从当前版本产生**，内容来源另行记录。

**状态**：生效中

## D-015 · 2026-10-01 · 设计：case_id 为不可变业务身份，编辑入口强制显式删除声明（细化 D-010）

## D-031 · 2026-10-13 · 设计：需求文档提取的字符清理——兼容汉字归一 + 无字形噪声剔除

**决策**：`extract_requirement_document` 在截断之前对提取正文做一次字符清理（`_normalize_extracted_text`），返回 `(正文, 剔除字符数)`，端点以 `dropped_chars` 回显、前端在解析提示里说明「已忽略 N 个无字形的符号」：①换行语义但不渲染的 `U+2028/U+2029/U+0085` 转为 `\n`、`U+00A0` 转为普通空格；②**逐字符** NFKC 归一康熙部首（U+2F00–2FDF）与 CJK 兼容汉字（U+F900–FAFF）为常规汉字（`租⼾`→`租戶`、`接收⼈`→`接收人`），刻意不做整体 NFKC，以免把全角标点/数字/序号一并改成半角；③剔除无字形噪声：C0/C1 控制符（`\n`/`\t` 除外）、私用区码位（Wingdings/Symbol 等符号字体残留）、替换字符 `U+FFFD`、零宽与双向控制符。剔除数量只回显不落库，也不保留正文副本。

**原因**：用户在「需求原文」里看到大量方框（□）。定位结论是这些方框来自**文档被解析出的字符本身**，不是页面或代码生成的：浏览器对"字体里没有字形"的字符只能画方框，而 PDF/Word 转文本常见的两类产物正好命中——(a) 康熙部首/兼容汉字（与常规汉字视觉几乎一致、码位不同，实测用户库中已有 `租⼾`(U+2F3E)、`接收⼈`(U+2F08)；Windows 的 msyh 覆盖这些码位，但 `simsun`/`msyhl` 不覆盖，字体回退落空时就是方框）；(b) 无字形码位（`U+FFFD` 在 msyh/simsun 中均无字形，必显示为方框，私用区符号字体残留同理）。这类字符不影响系统运行（不进 JSON 解析、不参与覆盖集合运算），但对 LLM 是纯噪声，且会被永久落库并随重新生成/发布复用，所以在入口清理最省事。选择 NFKC 逐字符而非自维护映射表：Unicode 自带定义、无需维护；选择回显剔除数量而非静默丢弃：让"文档里有解析不出的符号"对用户可见（原文若确有价值内容，用户可在可编辑的回填文本框里补回）。

**状态**：生效中

## D-034 · 2026-10-13 · 设计：表格单元格内的换行与跨页续排——续行折叠回单元格

**决策**：`utils/pdf_layout.py` 增加"续行折叠"：①判据是"行内不止一列且与列起点对齐"才算表格的新记录（`_rows_align` 追加**首格必须落在第一列**——只有后续列有内容的行几何上与"上一格换行"无法区分，按后者处理）；②**单元格内的换行/嵌套列表**满足"文本仍在表格横向范围内（左边界允许 4pt 悬挂缩进）+ 行距（顶到顶，与字号无关）不超过表内最近行距 ×1.8（下限 24pt）"即折叠进上一条记录的对应列（按列区间定位，`<br>` 连接，Markdown 表格单元格不能有真实换行）；③行距明显变大或起点在表格左边界之外的行结束表格（实测真实文档里正文起点 28.7pt 在表格首列 35.5pt 左侧、且与末行间距 43.5pt≈1.9 倍行距，两条判据各自都能拦住）；④各页行拼接后再统一渲染，**跨页续排的表格**不再被页边界截断（页内留空行的逻辑只在表格块之外生效）；⑤`to_markdown_table` 把单元格内的换行统一转 `<br>`（docx 单元格多段落同样受益）。

**原因**：用户实测反馈"表格内有多行时，格式不对"——真实文档的 `批量发送策略`/`发送通道`/`接收人指定方式` 三行的描述单元格里各自带多级列表与换行，原判据（整行 + 列对齐）在遇到第一个续行时即 flush，表格被拦腰截断，后续行退化成正文（"发送通道  必选，多选" 加一串散落的列表项）。这类"格内多行"在需求表格里极常见（下拉选项、子规则通常列在单元格内），不折叠等于把结构化信息再次打散，而折叠后字段与规则仍严格对应。选择 `<br>` 而非空格拼接：Markdown 表格不允许单元格内真实换行，`<br>` 是通行写法且保留原版面；选择"行距/左边界"而非"格数"作为表格边界判据：格数在"格内换行"与"该格为空"之间不可分，而版面几何可分。

**状态**：生效中

## D-036 · 2026-10-13 · 设计：测试任务五阶段化——"测什么"与"怎么测"分离，覆盖校验改为对照测试点清单

**决策**：测试任务的图从「需求分析 → 人工确认 → 用例生成 → 覆盖检查」细化为五阶段，每个阶段的产物都落库为 Artifact（`artifact_type` 直接新增，无需 schema 迁移）：

① 阶段与产物：**需求分析**（`requirement_analysis`）→ **测试点设计**（`test_point_set`）→ **测试设计策略**（`test_design_plan`）→ **用例生成**（`test_case_set`）→ **覆盖校验与质检**（`coverage_report`）。

② 阶段语义对齐 ISTQB CTFL v4.0：需求分析 = 测试依据分析与缺陷识别；测试点设计 = **测什么**（test condition）；测试设计策略 = **怎么测**的技术选型与覆盖项骨架；用例生成 = 用例实例化；覆盖校验 = 覆盖度量与质量检查（对应 test analysis / test design / coverage items / traceability 的既有划分）。

③ 归属澄清：业务流程（主流程/异常流程）的**测试视角路径枚举**归测试点设计，需求分析阶段不再重复产出；需求分析保留 ISTQB 明确纳入 test analysis 的"测试依据缺陷识别"（歧义、冲突、缺口，落在 `assumptions`），并补 `roles` / `constraints` / `preconditions` 三个需求级字段。

④ 技术归属：测试点阶段只产出"测什么 + 覆盖维度 + 风险/优先级"，**不产出具体取值**；等价类/边界值/判定表/状态迁移的**技术适用性判定与覆盖项骨架由确定性规则产出**——这是 D-020（测试设计=确定性规则引擎为主，LLM 仅补业务语义）从 API 域推广到工作流域；只有覆盖项的取值填充与业务语义分支交给 LLM。

⑤ 人工确认主位从"需求分析之后"移到"测试点与设计策略之后"：评审测试点的成本远低于评审几十条用例，而"测什么"错了后面全错。需求分析后的确认点保留，用于澄清歧义与冲突。（若人工在第二个 gate 修改了测试点，设计策略由确定性代码**重算**并追加新版本，不接受人工直接编辑——确定性产物手改会与规则脱节。）

⑥ 追溯链固化为 **需求点 → 测试点 → 用例**：用例新增 `test_point_refs`（覆盖的测试点）与 `covered_items`（覆盖项）、测试数据独立成字段。覆盖校验因此从"用例 `requirement_refs` 的**自我声明**"（现 `CoverageReport.note` 自认的缺陷）升级为**对照测试点/覆盖项清单逐项核对**，并补维度分布与质量问题清单。

⑦ 覆盖维度补齐非功能质量属性（ISO 25010 / MFQ 的 QC：性能、安全、兼容、可靠性）——现生成提示词的维度清单（功能/流程/状态/权限/接口/异常/边界）系统性缺失该维度。

⑧ 实现约束：**产物边界 5 层不等于 5 次 LLM 调用**。LLM 调用为 需求分析 1 次 + 测试点设计 1 次 + 用例生成 N 次（**按测试点分批**），阶段 3 与阶段 5 零 LLM；分批生成同时替代单次大批量输出，消除对 `WORKFLOW_LLM_MAX_TOKENS` 的强依赖与 `_salvage_truncated_json` 抢救路径的常态化。

**原因**：现状是需求分析产物**直接**作为用例生成的输入（`workflows/nodes.py` 的 `test_case_generation_agent` 只消费 `requirement_analysis`），覆盖维度（功能/流程/状态/权限/接口/异常/边界）以清单形式**埋在生成提示词内部**——用户既没有可评审的中间产物，代码也没有可校验的对象，只能靠 LLM 一次输出同时完成"想清楚测什么"和"写出可执行用例"两件事。后果有三：一是"测什么"完全不可见、不可改，用户在唯一的确认点上只能确认需求分析，看到用例时已经无法低成本纠偏；二是覆盖报告只能做集合运算式的自我声明校验（用例说覆盖了就认为覆盖了），无法回答"该测的方面有没有漏"；三是单次生成受 token 上限约束，需求点多时必然出现 uncovered 或截断（`_dynamic_case_limit` 的上限推算与截断抢救都是这一约束的症状）。主流做法（ISTQB 的 what/how 分离、国内 MFQ & PPDCS 的"测试分析输出测试点 → 测试设计输出用例"）都把"确定测什么"作为独立且**可评审**的产物，测试点正是成本最低、杠杆最高的评审对象。成本方面可控：新增的只有 1 次测试点设计调用（阶段 3、5 零 LLM），而按测试点分批生成后单批输出更小、失败可隔离重试，总 token 与峰值 token 都不高于现状。

**否决的备选**：①**只在生成提示词里补覆盖维度清单**——无中间产物、不可评审、不可确定性校验，等于维持现状。②**"测试点+用例"单产物一次生成**——测试点无法单独评审，也失去分批生成的 token 收益。③**阶段 3 也由 LLM 全量决策技术选型**——与 D-020 冲突、输出不可复现，且技术适用性本就是可用启发式判定的确定性规则。④**不引入测试点，直接给用例加"覆盖维度"标记**——覆盖校验退化为对 LLM 自我标注的统计，与现状同类。

**状态**：生效中

## D-038 · 2026-10-13 · 设计：新建测试任务保持独立页面，不改成弹窗

**决策**：`/workflow-new`（任务名称 + 需求原文 + 需求文档上传 + 知识库选择）保持**独立页面**，不改造成弹窗——即使一级菜单内的另外两个创建入口是弹窗（新建知识库、导入 OpenAPI）。交互形式按"表单体量"分档，而不是按"按钮长得一样"拉齐：

③ **长文本 + 附件 + 异步反馈 → 独立页面**：新建测试任务。需求原文上限 5 万字符，支持上传 PDF/Word/TXT/MD 异步解析并**追加**回填到已输入内容之后，解析状态要显示字符数、截断与剔除字符数，还有一个可移除的来源文档 chip；创建成功后必然跳 `/workflow-detail` 并启动长跑任务。

**否决的备选**：①**改成 760px 大弹窗**——宽度够放 14 行粘贴框（导入 OpenAPI 已证明），但没解决长文本编辑、上传解析状态与"提交后必跳转"这三件事。②**改成右侧抽屉**——能保留列表上下文且比弹窗宽，是唯一有实质收益的替代，但要新写抽屉样式并处理 `?new=1` 深链同步（入口链接要改），收益不抵成本。③**反方向统一：把导入 OpenAPI 也改成页面**——与"短任务就地完成"的既有模式背离，且它没有需要留驻的表单状态。④**统一按钮样式后仍强行统一交互形式**——样式一致（按钮、搜索框已抽到 nav.css 公共分节）与交互形式一致是两件事，按表单体量分档才是一致。

② **区块默认折叠，只留一行摘要**（`.edit-digest`）：摘要是折叠态唯一可见的内容，要讲清"里面有什么"——条目区块给「共 N 条 · 首条：…」，字段区块逐字段给「标签 + 条数」，「需求概述」这种单句字段直接显示正文摘要；点「展开」才出现字段，收起时重算（`syncSectionDigest`）不会显示过期内容；
③ **列表类字段用多行文本域，每行一条**（原来是"可编辑行 + Enter 新增 + 行尾 ✕"）：粘贴整段、批量改行都更直接，也省掉了一套行增删的 DOM 交互；
④ **条目卡默认折叠成一行纯文本**（编号 + 属性 + 标题 + 摘要，超长省略号）：需求点/风险给「编号 · [等级] · 标题 · 说明」，测试点给「编号 · 标题 · 维度 · 优先级 · 风险 · 要点描述」，用例给「编号 · 标题 · 优先级 · 自动化 · 步骤摘要」；点条目右侧「展开」才出现输入框、「收起」回收，新增条目自动展开并聚焦首个字段；
⑤ **字段统一是「左标签 + 右控件」**（`.edit-field`，短控件并排用 `.edit-inline`）；需求分析的标签列比其它卡宽一档（96px，窄屏改为标签在上、控件在下），因为分析字段名更长（"业务前置条件""歧义与待确认项"）；
⑥ **多行文本域随内容长高**（`autoGrowTextarea`：输入时与展开时重算，CSS 去掉拖拽把手并设 `overflow-y: hidden`）：固定行数在长内容时会出现内部滚动条，一屏十几个小滚动条既碎又堵；折叠状态下量不出高度（`scrollHeight` 为 0），所以每个展开动作里都要重算一次。

④⑥ 都是被实际使用打回来的：先改成卡片解决了"看不出字段是什么"，但需求点常有几十条、每条一个说明框，整页依然是文本框铺满（用户三次反馈"太多编辑框""还是太密集"）。所以最终形态是**逐级按需展开（区块 → 条目）+ 文本域贴合内容**：默认视图就是一张目录，展开谁才占谁的位置。

**组件化位置（三个编辑器共用）**：结构与样式收在 `nav.css` 的 `.edit-*` / `.row-remove` 一节（含折叠切换、摘要行、字段、输入控件），构造器与折叠/长高机制收在 `common.js`（`editInput`/`editSelect`/`editTextarea`/`editField`、`summarySpan`、`buildCollapseToggle`、`buildRowRemoveButton`、`setCardCollapsed`、`autoGrowTextarea(s)`）。页面脚本只做两件事：用这些构造器拼自己的字段、给卡片挂 `card.syncSummary` 回调写自己的摘要文案。契约是控件带 `data-sub="<字段名>"`（用例编辑器原来用 `data-field`，一并改成 `data-sub`，与容器上的 `data-field` 区分开）。命名从测试点专用的 `tp-*` 改成中性的 `edit-*`，就是为了让用例集详情页也能名正言顺地复用。

**实现要点**：折叠只切 CSS（`.edit-card.collapsed` / `.edit-section.collapsed` 切换摘要与正文的显隐），**输入框始终留在 DOM 里**，所以页面收集表单时不需要区分折叠态、也不存在"折叠时丢值"；折叠瞬间把最新值写回摘要行（各页的 `syncSummary` 回调 / `syncSectionDigest`），摘要不手工维护。副作用是"隐藏时量不出文本域高度"，因此约定：**新增任何"展开/显示"入口都要补一次 `autoGrowTextareas(root)`**。

**同时修掉的缺陷**：表单模式收集数据时以「原产物为基底、只覆盖表单管理的字段」取代原来的「凭表单重建整个对象」。原实现漏了 `roles` / `constraints` / `preconditions` 三个 schema 字段，用表单模式改一次需求分析再确认，这三个字段会被静默清空（`RequirementAnalysis` 的 `default_factory=list` 让缺失键悄悄变成空列表），下游测试点设计与提示词随之丢掉这部分输入。改成以产物为基底后，schema 新增字段或 JSON 模式里手写的额外字段也不会再被表单保存丢掉。

**原因**：同一个产品里三套编辑语言并存——工作流的测试点是"卡片 + 标签 + 输入控件"、需求分析却是"一片可编辑文字块"、用例集详情的用例编辑又是"label 在上 + 多行 flex 平铺"；用户每换一个页面就得重学一套操作。列表字段看不出字段边界，长文本没有多行容器，风险等级靠猜。统一后心智模型一致：**能编辑的东西都在折叠卡片里、都带标签、长文本都能多行、条目都能加/删**，默认视图是目录而不是一整屏输入框。
